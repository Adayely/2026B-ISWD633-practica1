# COMPLETAR  
Antes de la práctica sabía que los contenedores eran entornos aislados, pero no tenía claro qué pasaba con los datos cuando se eliminaba uno. Pensaba que al borrar un contenedor se perdía todo. Después de la práctica entendí que los contenedores son efímeros y que, para conservar la información, hay que guardar los datos fuera de ellos. Aprendí los tres tipos de almacenamiento. El bind mount vincula una carpeta del computador con una carpeta del contenedor, y lo usé con WordPress y MySQL, donde comprobé que al eliminar y recrear el contenedor el sitio, la personalización y las entradas se mantenían. El volumen nombrado lo gestiona Docker y se identifica por un nombre, y lo usé con Postgres y Drupal. Es más fácil de reutilizar y administrar porque no depende de rutas del computador. El volumen anónimo se crea sin nombre, con un identificador único, sirve para datos temporales y es difícil de referenciar después. Se elimina junto con el contenedor usando docker rm -fv, y los que quedan huérfanos se limpian con docker volume prune.

Durante la práctica se presentaron varios problemas. El primero fue que Drupal no se conectaba a la base de datos y mostraba el error connection to server at "localhost" failed: Connection refused. Dentro del contenedor de Drupal, localhost es el propio contenedor y no el de Postgres, así que lo resolví usando como host el nombre del contenedor, server-postgres, en las opciones avanzadas de la instalación. Con esto aprendí que en una red de Docker los contenedores se encuentran entre sí por su nombre.

El segundo problema fue que el contenedor de Postgres se detenía apenas iniciaba. Con docker ps -a vi que estaba en estado Exited (1), y con docker logs server-postgres descubrí que la imagen sin versión había descargado Postgres 18, que ya no acepta el volumen montado en /var/lib/postgresql/data. Lo resolví eliminando el contenedor y el volumen, y recreándolos con la imagen postgres:16. De ahí aprendí que conviene fijar la versión de las imágenes para evitar cambios inesperados.

El tercer problema fue un conflicto de puertos: pgAdmin intentaba usar el puerto 9500, que ya estaba ocupado por el contenedor de WordPress, así que lo publiqué en el puerto 9600. Aprendí que un puerto del host solo lo puede usar un contenedor a la vez. Por último, el contenedor de pgAdmin salió con el código 137, que indica que el proceso fue detenido, por ejemplo por falta de memoria o por un reinicio de Docker, y lo resolví recreándolo.

Además de los comandos que menciona la guía, utilicé los comandos mencionados en clase como docker ps para ver los contenedores en ejecución y docker ps -a para ver también los detenidos y su estado. Usé docker logs para encontrar la causa de un contenedor que se caía y docker network inspect para verificar qué contenedores estaban conectados a la red. También usé docker rm -f para detener y eliminar contenedores en un solo paso y docker volume ls para listar los volúmenes existentes.

Esta práctica me ayuda a desplegar aplicaciones completas, con servidor web, base de datos y cliente de administración, de forma reproducible y sin instalar nada directamente en mi computador. Saber separar la aplicación de sus datos es clave para actualizar, migrar o recuperar servicios sin perder información.
